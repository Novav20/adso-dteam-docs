# ADR-009: Internationalization (i18n) Strategy for Blazor Frontend

## Context
The application interface needs to support localization to prevent hardcoded strings in the UI, especially given its deployment in different regions (e.g., a Colombian single-tenant plant requiring full Spanish UI). Hardcoding text directly into `.razor` components violates maintainability principles and prevents easy updates or expansion to multi-language deployments in the future. We need a standardized approach to manage translations across the Blazor application.

## Decision
We will adopt the standard **.NET `Microsoft.Extensions.Localization`** pattern for the Blazor WebAssembly/Server application:
1. **Resource Files (.resx):** UI strings will be extracted into structured `.resx` files. We will use a centralized resource file (e.g., `AppResources.resx`) for common strings and component-specific resource files when appropriate for complex views.
2. **`IStringLocalizer` Injection:** Components will inject `IStringLocalizer<T>` to retrieve localized strings at runtime.
3. **Culture Management:** The application will determine the culture based on the user's browser settings or an explicit user profile preference, falling back to a default culture (e.g., `es-CO` or `en-US`).
4. **No Hardcoded UI Text:** All new Razor components and screens (including `SCR-VIS-033`) must use localization keys instead of raw text literals.

## Alternatives Considered
* **Custom JSON-based localization service:** Rejected. While lightweight, it bypasses the native ecosystem tools and conventions provided by .NET, missing out on compile-time checking and tooling support for `.resx` files.
* **Hardcoding Spanish strings globally:** Rejected. Although the current deployment is for a single-tenant Colombian plant, tying the codebase strictly to one language severely limits future scalability and violates clean architecture principles.

## Consequences
* **Positive:** Complete separation of text resources from UI structure. Easy translation by non-developers using standard `.resx` editors.
* **Negative:** Slight overhead in developer workflow, as every string must be added to a resource file before use. Minor initial setup required in `Program.cs` to configure localization middleware.
