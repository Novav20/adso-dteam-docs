# ADR-011: .NET Aspire for Local Orchestration, Observability, and Integration Testing

## Context
DTEAM combines a .NET 10 Modular Monolith (`Dteam.Api`), a Blazor Web App administrative portal (`Dteam.Web`), a .NET MAUI Blazor Hybrid field client (`Dteam.Mobile`), PostgreSQL 18 with TimescaleDB, Redis 7.x, Azure Blob Storage, and industrial telemetry streams (Azure IoT Hub / MQTT). Coordinating these dependencies manually during local development and integration testing creates configuration drift (ports, connection strings, health probes, and OpenTelemetry wiring) and makes debugging real-time SignalR streams (such as the 2-second LOTO safety heartbeat) slow and error-prone.

At the same time, the production MVP deployment topology is already fixed on Docker Engine over a Linux VPS ([DT-ARQ-DEP-DOC-001](../views/DT-ARQ-DEP-DOC-001.md)).

## Decision
We adopt **.NET Aspire** (`Dteam.AppHost` and `Dteam.ServiceDefaults`) strictly for **local development orchestration, OpenTelemetry observability, and automated integration testing (`Aspire.Hosting.Testing`)**, while preserving the existing **Docker Engine on Linux VPS** production deployment architecture:

1. **`Dteam.AppHost` (Local Orchestration):** Orchestrates `Dteam.Api`, `Dteam.Web`, PostgreSQL 18 + TimescaleDB container, Redis 7.x container, and an optional local MQTT broker container (Mosquitto) for SCADA telemetry emulation with deterministic service discovery and injected connection strings.
2. **`Dteam.ServiceDefaults` (Observability & Resilience):** Standardizes OpenTelemetry distributed tracing, structured logging, health checks (`/health`, `/alive`), and HTTP resilience policies across `Dteam.Api` and `Dteam.Web`, enabling end-to-end tracing across Minimal APIs, SignalR hubs, and PostgreSQL queries.
3. **Mobile Client Boundary (`Dteam.Mobile`):** Because .NET MAUI Blazor Hybrid executes on Android/iOS field devices rather than a server host, `Dteam.Mobile` is not orchestrated inside `Dteam.AppHost`; during local testing it connects to the Aspire-hosted `Dteam.Api` via local network IP or dev tunnels.
4. **Integration Testing:** `Dteam.Integration.Tests` uses `Aspire.Hosting.Testing` (paired with PostgreSQL 18 + TimescaleDB) to validate recursive CTEs, `xmin` optimistic concurrency, WORM audit RLS policies (`FORCE ROW LEVEL SECURITY` + `REVOKE UPDATE, DELETE`), and SignalR hubs against real database containers.

## Alternatives Considered

* **Alternative 1: Manual `docker-compose.yml` + Hand-Wired OpenTelemetry**
  * *Status:* Rejected.
  * *Reasoning:* Requires maintaining duplicate port mappings, environment variables, and connection strings across developer workstations, CI integration tests, and `.csproj` launch profiles, without providing an integrated local trace/SignalR dashboard.
* **Alternative 2: Full .NET Aspire Production Deployment (Azure Container Apps / Kubernetes)**
  * *Status:* Rejected.
  * *Reasoning:* Conflicts with the MVP cost and operational baseline defined in [DT-ARQ-DEP-DOC-001](../views/DT-ARQ-DEP-DOC-001.md), which targets single-node Docker Engine on a Linux VPS behind Nginx and TLS 1.3.

## Consequences
* **Positive:** Single-command (`F5` / `dotnet run`) local environment startup; unified OpenTelemetry tracing for SignalR LOTO heartbeats and cross-DbContext transactions; reproducible container-backed integration tests.
* **Negative / Guardrail:** Production Dockerfiles and Nginx reverse-proxy manifests in `DT-ARQ-DEP-DOC-001` must remain decoupled from `Dteam.AppHost` so production deployments never depend on Aspire-specific cloud manifests.
