# ADR-006: Offline Conflict Resolution via Command Queuing and Cryptographic Leases

## Context
The DTEAM system operates under a disconnected mobile topology. Initially, conflict resolution via *Last-Write-Wins* (LWW) based on physical client timestamps was proposed. 
Risk analysis in Oil & Gas operations revealed critical flaws in this strategy:
1. **Kardex Imbalance (Transaction Loss):** If two technicians consume parts in offline mode, LWW overwrites the inventory state based on the most advanced clock, erasing the record of one of the consumptions and breaking the cost traceability required by ISO 55001.
2. **Fatal Risk in LOTO (Clock Drift / NTP Skew):** If a supervisor revokes an emergency permit and an offline technician updates the task status with a clock drifted by milliseconds, LWW overwrites the safety revocation, enabling work on energized lines.

## Decision
Overwriting states via *Last-Write-Wins* (LWW) is formally discarded. Instead, a hybrid model adapted to the modular monolith architecture in .NET is adopted:

1. **Command-Sourced Synchronization for Business and Inventory:**
   * The mobile app does not synchronize mutated states (e.g., `Stock = 5`), but rather atomic commands in a local SQLite `SyncOutbox` queue (e.g., `ConsumeSparePart(Id, PartId, Qty, WorkOrderId)`).
   * The `Background Sync Worker` transmits the commands in FIFO order.
   * The .NET server processes each command sequentially and idempotently within an EF Core transaction, impacting the transaction ledger (`inv.inventory_transactions`). If a consumption causes a negative balance, the server records the physical discrepancy and triggers a compensation/alert flow without losing historical authorship.

2. **Offline Leases for LOTO Safety:**
   * The central server issues a bounded temporary authorization token (e.g., a maximum 1-hour window) to the mobile device, signed via HMAC-SHA256 with a provisioned symmetric key.
   * The mobile application only allows registering progress or interactions in LOTO procedures as long as the lease time has not expired locally.
   * If the time expires without reconnection, the interface is automatically blocked for safety, forcing the technician to re-establish the link or request a physical manual override, narrowing the discrepancy risk to a known and auditable time window.

## Alternatives Considered
* **CRDTs (Conflict-Free Replicated Data Types via PN-Counters / `cr-sqlite`):** Rejected. They cannot validate edge invariants ($Stock \ge 0$) during network partitions, do not support foreign keys in SQLite, and add disproportionate complexity for a solo developer.
* **Full Event Sourcing:** Rejected. It would introduce massive maintenance overhead by forcing the versioning of event schemas and read projections across the entire MVP database.

## Consequences

### Positive
* Elimination of lost accounting records and spare part consumption transactions.
* Regulatory shielding of failure and cost history for ISO 55001 audits.
* Mitigation of LOTO collision risks via verifiable cryptographic time boundaries.

### Negative
* Requires implementing an explicit command dispatch handler (`SyncOutbox`) on the mobile client and idempotent controllers in the .NET API.

### Risks and Technical Debt
* If the tablet's OS date and time are deliberately altered by the user, it could prematurely invalidate the LOTO lease. This will be mitigated by using the hardware's internal monotonic clock.
