# ADR-006: Offline Conflict Resolution via Command Queuing and Cryptographic Leases

## Context
The DTEAM system operates under a disconnected mobile topology. Initially, conflict resolution via *Last-Write-Wins* (LWW) based on physical client timestamps was proposed. 
Risk analysis in Oil & Gas operations revealed critical flaws in this strategy:
1. **Kardex Imbalance (Transaction Loss):** If two technicians consume parts in offline mode, LWW overwrites the inventory state based on the most advanced clock, erasing the record of one of the consumptions and breaking the cost traceability required by ISO 55001.
2. **Fatal Risk in LOTO (Clock Drift / NTP Skew):** If a supervisor revokes an emergency permit and an offline technician updates the task status with a clock drifted by milliseconds, LWW overwrites the safety revocation, enabling work on energized lines.

## Decision
Overwriting states via *Last-Write-Wins* (LWW) is formally discarded. Instead, a hybrid model adapted to the modular monolith architecture in .NET is adopted:

1. **Command-Sourced Synchronization for Business and Inventory:**
   * The mobile app does not synchronize mutated states (e.g., `Stock = 5`), but rather atomic commands in a local SQLite `SyncOutbox` queue (e.g., `ConsumeSparePart(Id, PartId, Qty, WorkOrderId)`).
   * **Client-Side UUIDv7 Identity Generation:** Any entity created offline on the mobile terminal (e.g., Work Requests, Failure Records, Media Attachments) assigns its immutable primary key locally at instantiation using .NET's native `Guid.CreateVersion7()`. This enables immediate construction of relational foreign-key graphs in SQLite without key re-mapping upon server sync, ensuring that records ingested by PostgreSQL preserve time-ordered sequential indexing ([ADR-005](./ADR-005.md)).
   * The `Background Sync Worker` transmits the commands in FIFO order.
   * The .NET server processes each command sequentially and idempotently within an EF Core transaction, impacting the transaction ledger (`inv.inventory_transactions`). If a consumption causes a negative balance, the server records the physical discrepancy and triggers a compensation/alert flow without losing historical authorship.

2. **Offline Leases for LOTO Safety:**
   * The central server issues a bounded temporary authorization token (e.g., a maximum 1-hour window) to the mobile device, signed via HMAC-SHA256 with a provisioned symmetric key.
   * The mobile application only allows registering progress or interactions in LOTO procedures as long as the lease time has not expired locally.
   * If the time expires without reconnection, the interface is automatically blocked for safety, forcing the technician to re-establish the link or request a physical manual override, narrowing the discrepancy risk to a known and auditable time window.
   * **Database Lock Delegation:** The central PostgreSQL engine recognizes the active lease as a distributed safety lease. While a lease is active for an asset, the central server defers synchronous row-level pessimistic locking (`SELECT ... FOR UPDATE NOWAIT`), transferring transient execution authority to the leaseholder's local SQLite database. Incoming telemetry during the lease window triggers supervisor warnings without locking or invalidating the disconnected client. Full state reconciliation and ledger updates execute upon reconnection via the `Background Sync Worker`.

## Canonical Offline, Watchdog & Session Constants

All offline-capable clients, perimeter watchdogs, and IAM token issuers MUST bind strictly to the following normative timing and TTL constants:

## Canonical 5-Step Offline Outbox & Two-Phase Media Sync Lifecycle

All disconnected field mutations and offline media captures MUST execute the single canonical 5-step protocol below:

1. **Step 1 — Local Encrypted Outbox & Binary Persistence (`SQLCipher`):** On network disconnection or HTTP 5xx timeout, the client serializes the domain command payload into the local SQLite `SyncOutbox` queue encrypted at rest via AES-256 SQLCipher (`IOfflineStorage`, [TR-002](../../requirements/common/TR-002.md), [TR-007](../../requirements/common/TR-007.md)). Any offline-captured multimedia binaries and their pre-computed SHA-256 checksums (`TR-003`) are stored encrypted locally linked to the queued command.
2. **Step 2 — Deterministic `UUIDv7` Identity & `X-Idempotency-Key` Assignment:** Offline-created records assign immutable primary keys locally via `Guid.CreateVersion7()` ([ADR-005](./ADR-005.md)), and every queued command is stamped at enqueue time with a unique `UUIDv7` `X-Idempotency-Key` header ([ADR-007](./ADR-007.md)) to guarantee exactly-once replay semantics.
3. **Step 3 — Omission of Stale `If-Match` Headers on Replay:** Whereas live online mutations enforce PostgreSQL `xmin` optimistic concurrency via `If-Match: "{ConcurrencyToken}"` ([DT-ARQ-DB-DOC-001 §3.12](../DT-ARQ-DB-DOC-001.md#312-optimistic-concurrency-control-via-postgresql-xmin-system-column-inv-027-nfr-169)), offline-queued replays MUST **omit stale `If-Match` headers** so extended connectivity blackouts do not cause silent HTTP 409 rejections upon reconnect. Disconnected LOTO mutations instead carry the signed `CryptographicOfflineLeaseDto` (`LeaseToken`) acquired before offline entry.
4. **Step 4 — FIFO Two-Phase Reconnect Sync ([ADR-008](./ADR-008.md)):** Upon connectivity restoration, the `Background Sync Worker` drains `SyncOutbox` strictly in chronological **FIFO** order:
   * **Phase 1 (Valet Key Media Upload):** For commands carrying locally encrypted attachments, the worker first requests a short-lived Azure Blob SAS Valet Key from the API (`POST /api/v1/maintenance/work-orders/{id}/media-upload-sas`), executes a direct `HTTPS PUT` of each binary directly to Azure Blob Storage (bypassing the monolith), and binds the returned remote `FileUrl` references into the queued command.
   * **Phase 2 (Idempotent Command Dispatch):** The worker replays the hydrated domain command carrying its preserved `X-Idempotency-Key` (without stale `If-Match`).
5. **Step 5 — Server Command-Sourced Merge & Reconciliation:** The backend validates `X-Idempotency-Key` against `IdempotencyLog` ([ADR-007](./ADR-007.md)), executes the command inside a single-commit ACID transaction (applying business invariants, appending immutable ledger/history rows, and sealing the SHA-256 audit chain per [ADR-003](./ADR-003.md)), and raises administrative reconciliation alerts on any concurrent state divergence (such as negative spare-part availability or parallel work-order updates) without losing field authorship.

## Alternatives Considered
* **CRDTs (Conflict-Free Replicated Data Types via PN-Counters / `cr-sqlite`):** Rejected. They cannot validate edge invariants ($Stock \ge 0$) during network partitions, do not support foreign keys in SQLite, and add disproportionate complexity for a solo developer.
* **Full Event Sourcing:** Rejected. It would introduce massive maintenance overhead by forcing the versioning of event schemas and read projections across the entire MVP database.

## Consequences

### Positive
* Elimination of lost accounting records and spare part consumption transactions.
* Regulatory shielding of failure and cost history for ISO 55001 audits.
* Mitigation of LOTO collision risks via verifiable cryptographic time boundaries.

### Negative
* Requires implementing an explicit command dispatch handler (`SyncOutbox`) on the mobile client and idempotent controllers in the .NET API.

### Risks and Technical Debt
* If the tablet's OS date and time are deliberately altered by the user, it could prematurely invalidate the LOTO lease. This will be mitigated by using the hardware's internal monotonic clock.
