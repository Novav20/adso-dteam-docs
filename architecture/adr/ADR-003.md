# ADR-003: Immutable Audit Architecture via Chained Hashing

## Context
Compliance with ISO 27001 and traceability in ISO 55001 require that audit logs cannot be altered. In standard relational databases, an administrator with physical access or elevated credentials can alter or delete records, affecting the application's traceability. Adopting specialized immutable ledger databases introduces high operational costs for the MVP phase.

## Decision
A **Tamper-Evident Ledger** architecture is implemented, structured in two layers:

1. **Row-Level Security in PostgreSQL:** Audit tables are configured with append-only policies. Update and delete commands are explicitly denied for the ORM connection user.
2. **Cryptographic Chaining in the Application Layer:** Upon insertion, the backend calculates a hash that concatenates the current payload with the integrity hash of the immediately preceding transaction.
3. **Meta-Audit:** Reading records dynamically verifies the chain and alerts the auditor in case of mathematical discrepancies.
4. **Atomic State Capture:** To populate the `previous_state` and `new_state` attributes without incurring previous reads (`SELECT`) that penalize latency, transactional mutations will leverage PostgreSQL 18's native ability to project atomic states via the `RETURNING old.*, new.*` clause. This ensures that audit capture is resolved in the same network round-trip as the main transaction (<50ms, conforming to TR-001-NFR-366).

## Alternatives Considered
* **Specialized immutable ledger cloud databases:** Rejected due to generating vendor lock-in and operational overhead for an MVP.
* **Triggers and history tables in the SQL engine:** Rejected. A trigger can be disabled by an attacker with database access without leaving an obvious cryptographic trail.

## Consequences

### Positive
* Ensures non-repudiation and detects external alterations in the database without third-party tools.
* Efficient storage of pre and post states thanks to the use of the JSON binary format.

### Negative
* Higher latency in writes due to the algorithmic calculation of the hash.
* Difficulty in purging individual records for data protection regulations without breaking chain validation.

### Risks and Technical Debt
* The mechanism does not prevent the complete deletion of the table. Protection against total destruction falls on infrastructure-level backup retention policies.
