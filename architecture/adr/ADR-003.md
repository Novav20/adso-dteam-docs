# ADR-003: Immutable Audit Architecture via Chained Hashing

## Context
Compliance with ISO 27001 and traceability in ISO 55001 require that audit logs cannot be altered. In standard relational databases, an administrator with physical access or elevated credentials can alter or delete records, affecting the application's traceability. Adopting specialized immutable ledger databases introduces high operational costs for the MVP phase.

## Decision
A **Tamper-Evident Ledger** architecture is implemented, structured in two layers:

1. **Row-Level Security in PostgreSQL:** Audit tables are configured with append-only policies. Update and delete commands are explicitly denied for the ORM connection user.
2. **Cryptographic Chaining in the Application Layer:** Upon insertion, the backend calculates a hash that concatenates the current payload with the integrity hash of the immediately preceding transaction.
3. **Meta-Audit:** Reading records dynamically verifies the chain and alerts the auditor in case of mathematical discrepancies.
4. **Atomic State Capture:** To populate the `previous_state` and `new_state` attributes (whose polymorphic JSONB envelope and transversal governance contract are specified in [DT-ERD-DOC-001 §6.7](../../domain-models/entity-relationship/DT-ERD-DOC-001.md#67-admaudit_logsprevious_state-and-new_state)) without incurring previous reads (`SELECT`) that penalize latency, transactional mutations will leverage PostgreSQL 18's native ability to project atomic states via the `RETURNING old.*, new.*` clause. This ensures that audit capture is resolved in the same network round-trip as the main transaction (<50ms, conforming to TR-001-NFR-366).

## Canonical Hash Formula & Audit Constants

To serve as the single authoritative definition across UI specifications, domain aggregates, and persistence interceptors, all chained WORM ledger verification and governance constraints adhere to the contract below:

1. **Authoritative WORM Hash-Chain Formula:**
   For chronological record $k$ ($k \ge 1$, anchored to $H_0 = \text{"GENESIS"}$ per [DT-ERD-DOC-001 §3.5.1](../../domain-models/entity-relationship/DT-ERD-DOC-001.md#351-audit_logs)):
   $$H_k = \text{SHA-256}\left(H_{k-1} \parallel \text{Id}_k \parallel \text{UserId}_k \parallel \text{ActionType}_k \parallel \text{EntityType}_k \parallel \text{EntityId}_k \parallel \text{TimestampUtc}_k \parallel \text{CanonicalJson}(\text{PrevState}_k) \parallel \text{CanonicalJson}(\text{NewState}_k)\right)$$
   where $\text{CanonicalJson}(\cdot)$ serializes polymorphic `JSONB` snapshots deterministically (lexicographically sorted keys, invariant UTC ISO-8601 timestamps, no insignificantly padded whitespace) so recalculation in forensic verification (`AuditLog.VerifyIntegrity()`) is deterministic across backend and browser `ICryptoInterop`.

2. **Server Authoritative Chain Hash vs. Client UI Preview Digest:**
   * **Server Authoritative Chain Hash ($H_k$):** Computed synchronously pre-commit inside the active shared `DbTransaction` by `AuditSaveChangesInterceptor` ([DT-ARQ-DB-DOC-001 §3.9](../DT-ARQ-DB-DOC-001.md#39-cross-dbcontext-atomic-transactions-idbcontexttransaction-sharing-tr-001-tr-005-inv-025)), which resolves $H_{k-1} = \text{audit\_logs.previous\_hash}$ directly on the server. Clients MUST NEVER supply `PreviousHash` in mutating commands, eliminating multi-client race conditions.
   * **Client UI Preview Digest:** Computed strictly for local operator visibility prior to command submission as $\text{SHA-256}(\text{CanonicalJson}(\text{CommandPayload}))$ (without a client-supplied `PreviousHash`). It serves exclusively as an informational payload digest preview and is never stored as $H_k$.

3. **Canonical Audit Governance Constants:**

   | Constant / Policy Parameter | Canonical Value | Governing Scope & Reference |
   | :--- | :--- | :--- |
   | **Minimum `AuditJustification` Length** | `>= 15` non-whitespace characters | Mandatory justification for audited updates, RIME overrides, SoD/PoLP reviews, commissioning rejections, taxonomy reorganizations, and LOTO overrides (`NewState` envelope per [DT-ERD-DOC-001 §6.7](../../domain-models/entity-relationship/DT-ERD-DOC-001.md#67-admaudit_logsprevious_state-and-new_state)). |
   | **WORM Ledger Retention Window** | `7 years` minimum | Declarative quarterly range partitioning with unbroken `PartitionAnchorHash` continuity across cold archives per [TR-001](../../requirements/common/TR-001.md#functional-requirements-fr) (`TR-001-FR-367`, ISO 55001 Clause 7.5). |
   | **Genesis Chain Anchor ($H_0$)** | `"GENESIS"` | Fixed sentinel predecessor hash for the first chronological ledger entry ($k = 1$). |
   | **Pre-Commit Capture Latency Budget** | `< 50 ms` (95th percentile) | Transactional audit capture + hash chaining inside the main Unit of Work per [TR-001](../../requirements/common/TR-001.md#non-functional-requirements-nfr) (`TR-001-NFR-366`). |

## Alternatives Considered
* **Specialized immutable ledger cloud databases:** Rejected due to generating vendor lock-in and operational overhead for an MVP.
* **Triggers and history tables in the SQL engine:** Rejected. A trigger can be disabled by an attacker with database access without leaving an obvious cryptographic trail.

## Consequences

### Positive
* Ensures non-repudiation and detects external alterations in the database without third-party tools.
* Efficient storage of pre and post states thanks to the use of the JSON binary format.

### Negative
* Higher latency in writes due to the algorithmic calculation of the hash.
* Difficulty in purging individual records for data protection regulations without breaking chain validation.

### Risks and Technical Debt
* The mechanism does not prevent the complete deletion of the table. Protection against total destruction falls on infrastructure-level backup retention policies.
