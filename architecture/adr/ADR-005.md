# ADR-005: Adopción de PostgreSQL 18 como Motor de Persistencia Relacional

## Contexto
El diseño del Gemelo Digital exige la persistencia de dos flujos de datos masivos y concurrentes: el registro de auditoría inmutable y la telemetría de sensores. Inicialmente se consideró PostgreSQL 16. Sin embargo, el uso de identificadores UUIDv4 (completamente aleatorios) fragmenta las páginas de los índices B-Tree en tablas de alto volumen, degradando el rendimiento de inserción. Adicionalmente, el requerimiento de auditoría ([[ADR-003]]) exige capturar el estado previo y nuevo de cada fila modificada con una latencia mínima.

## Decisión
Se adopta **PostgreSQL 18** como el motor relacional base para el proyecto DTEAM. 
La arquitectura explotará dos características nativas exclusivas de esta versión:
1. **Generación nativa de `uuidv7()`:** Se utilizará como valor por defecto para todas las llaves primarias. Al estar ordenados cronológicamente (48 bits de timestamp), las inserciones se añaden secuencialmente a la última hoja del árbol B-Tree, maximizando el rendimiento de disco.
2. **Cláusula `RETURNING old.*, new.*`:** Se empleará en el `SaveChangesInterceptor` de Entity Framework Core para capturar el estado atómico antes y después de una mutación en un solo viaje de red.

## Alternativas Consideradas
* **PostgreSQL 16 o 17 con extensión `uuid-ossp`:** Rechazado. Obliga a depender de extensiones para la generación de UUIDs y no resuelve la fragmentación nativa de índices a menos que se implementen rutinas personalizadas de secuenciación, lo cual añade deuda técnica.

## Consecuencias

### Positivas
* Rendimiento de inserción sostenido en tablas masivas (telemetría, logs) gracias a los identificadores secuenciales en el tiempo.
* Reducción de la latencia de red al eliminar sentencias `SELECT` previas para auditoría de mutaciones.

### Negativas
* Obliga a utilizar las imágenes Docker más recientes (Edge/Latest) del motor de base de datos durante el desarrollo.

### Riesgos y Deuda Técnica
* **Compatibilidad de Extensiones:** Se asume el riesgo temporal de que extensiones críticas como TimescaleDB presenten retrasos de compatibilidad durante las primeras actualizaciones menores de PostgreSQL 18. Esto requerirá validación de la imagen de contenedor antes del pase a producción.
