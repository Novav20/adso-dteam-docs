# ADR-005: Adoption of PostgreSQL 18 as the Relational Persistence Engine

## Context
The Digital Twin design requires the persistence of two massive and concurrent data streams: the immutable audit log and sensor telemetry. Furthermore, the system operates in an offline-first topology where entities (such as Work Requests and Failure Records) originate on disconnected mobile tablets ([[ADR-006]]). Initially, PostgreSQL 16 was considered. However, the use of UUIDv4 identifiers (completely random) fragments B-Tree index pages in high-volume tables, degrading insertion performance. Additionally, the audit requirement ([[ADR-003]]) demands capturing the previous and new state of each modified row with minimal latency.

## Decision
**PostgreSQL 18** is adopted as the base relational engine for the DTEAM project. 
The architecture will exploit two native features exclusive to this version, coordinated with the application layer:
1. **Sequential UUIDv7 Identifiers across Application and Database Layers:**
   * **Application Layer Authority:** To support offline-first operations ([[ADR-006]]) without key re-mapping or index fragmentation, primary key generation is mastered at the Application Layer in .NET using native `Guid.CreateVersion7()`. Both the .NET MAUI mobile app and the ASP.NET Core backend assign immutable, time-ordered UUIDv7 identifiers at entity creation before local SQLite persistence or transmission.
   * **Database Fallback:** The PostgreSQL 18 native `DEFAULT uuidv7()` constraint is maintained across all table definitions ([[DT-ERD-DOC-001]]) as an engine-level safety net and default for server-originated infrastructure records (e.g., `adm.audit_logs`).
   * Because client-generated IDs are genuine UUIDv7s, index page fragmentation in PostgreSQL B-Trees is prevented upon synchronization.
2. **The `RETURNING old.*, new.*` clause:** It will be used in the Entity Framework Core `SaveChangesInterceptor` to capture the atomic state before and after a mutation in a single network round-trip.

## Alternatives Considered
* **PostgreSQL 16 or 17 with `uuid-ossp` extension:** Rejected. Forces dependency on extensions for UUID generation and does not solve native index fragmentation unless custom sequencing routines are implemented, which adds technical debt.

## Consequences

### Positive
* Sustained insertion performance in massive tables (telemetry, logs) thanks to time-sequential identifiers.
* Seamless offline foreign-key graph construction on mobile clients without requiring server key re-mapping or B-Tree index fragmentation.
* Reduction of network latency by eliminating previous `SELECT` statements for mutation auditing.

### Negative
* Forces the use of the latest Docker images (Edge/Latest) of the database engine during development.

### Risks and Technical Debt
* **Extension Compatibility:** We assume the temporary risk that critical extensions like TimescaleDB may experience compatibility delays during the first minor updates of PostgreSQL 18. This will require container image validation before going to production.
