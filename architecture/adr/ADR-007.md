# ADR-007: Two-Tier Hybrid Idempotency Architecture (Redis + PostgreSQL)

## Context
The Digital Twin and EAM system requires absolute data integrity across distributed transaction boundaries. Field technicians utilize a .NET MAUI mobile application operating in offline-first mode to perform safety-critical operations, such as Lockout/Tagout (LOTO) isolations. When network connectivity is restored, the client flushes a queued backlog of requests over unstable industrial wireless channels. 

Network instability frequently creates "retry storms" where requests reach the backend and trigger state mutations, but the returning HTTP `200 OK` acknowledgment drops in transit. Without exactly-once execution semantics, these retries expose the core domain to critical failure modes, including duplicated safety isolations. The backend interceptor (implemented as an `IAsyncActionFilter` across 5 Kubernetes pods) must deduplicate these requests without causing database lock contention or distributed state corruption.

## Decision
We will adopt a **Two-Tier Hybrid Architecture** that combines the low latency of a Redis Cluster with the strict ACID transaction guarantees of PostgreSQL 18.

1. **Stage 1 (Ingress Fast-Path):** The ASP.NET interceptor extracts the `Idempotency-Key`, computes a canonical SHA-256 fingerprint of the payload (to prevent payload mutation), and issues an atomic `SETNX` lock to Redis with a 30-second `IN_PROGRESS` lease. This absorbs heavy retry storms with ~0.5ms latency without touching the relational database.
2. **Stage 2 (Atomic Persistence):** During domain execution, a durable `IdempotencyLog` record is inserted into PostgreSQL *within the exact same explicit database transaction* as the business mutation (e.g., LOTO status update). 
3. **Stage 3 (Synchronization):** 
   - On successful commit: The Redis key is updated to `COMPLETED` containing the JSON response and given a 24-hour TTL.
   - On exception/rollback: The interceptor executes a `REDIS DEL` command to immediately release the transient lock, allowing subsequent retries to process cleanly.
4. **Maintenance:** The PostgreSQL `IdempotencyLog` table will be range-partitioned by day to allow fast `DROP TABLE` partition cleanup, avoiding MVCC dead-tuple bloat.

## Alternatives Considered

* **Strategy 1: Pure PostgreSQL (`IdempotencyLog` Table Only)**
  * *Status:* Rejected.
  * *Reasoning:* Places extreme overhead on the database during peak sync conditions. It degrades hot-path latency by 10ms–50ms due to mandatory WAL disk flushes and generates massive Multi-Version Concurrency Control (MVCC) bloat and `autovacuum` load.
* **Strategy 2: Pure Redis Cluster (`SETNX` Only)**
  * *Status:* Rejected.
  * *Reasoning:* Introduces a severe "Dual-Write Disjoint State Vulnerability". If Redis locks the key but the PostgreSQL domain transaction fails (e.g., due to a deadlock), the cache retains a success state. A retry would falsely inform the technician that a safety lockout was applied when the database has no record of it, leading to catastrophic safety data corruption.
* **Strategy 3: Local Container In-Memory Cache (`.NET IMemoryCache`)**
  * *Status:* Rejected.
  * *Reasoning:* Architecturally invalid for multi-replica environments. Process memory is incoherent across Kubernetes pods; if a load balancer routes a retry to a different pod, the local cache lookup fails and the transaction is duplicated.
