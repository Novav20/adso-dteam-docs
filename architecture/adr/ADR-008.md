# ADR-008: Selection of Azure Blob Storage for ISO 14224 Multimedia Evidence

## Context
The CMMS Digital Twin requires field technicians to capture and upload high-resolution photographic and video evidence linked to specific `FailureRecords` (ISO 14224 compliance). Storing these binary payloads natively inside the PostgreSQL database using `bytea` (Relational BLOB storage) introduces severe operational bottlenecks. As verified via Deep Research (GN), it rapidly saturates `shared_buffers`, explodes Write-Ahead Log (WAL) generation, and exponentially inflates database backup/restore times, threatening RTO objectives. 

To protect relational database performance, the architecture requires the **Valet Key Pattern**, where the .NET 10 API acts as an authorization broker, providing the client with a Time-Limited Signed URL to upload the payload directly to a specialized cloud Object Store. The database will only store the resulting file URI.

## Decision
We will adopt **Azure Blob Storage** as the primary Object Storage provider and implement the **Valet Key Pattern** using Shared Access Signatures (SAS). 
The `.NET 10` API will authenticate against Azure using Managed Identities (`DefaultAzureCredential`), generate user-delegated SAS tokens, and return them to the `mobile_app` client. The client will execute direct HTTP PUT requests to Azure, bypassing the backend server's memory and network stack entirely.

## Alternatives Considered
* **Amazon S3:** Evaluated as a highly resilient and ubiquitous alternative. Rejected because, while standard, Azure Blob Storage offers superior, native SDK synergy (`Azure.Storage.Blobs`) with our .NET 10 / ASP.NET Core stack and frictionless Microsoft Entra ID (Managed Identities) integration.
* **Relational BLOB Storage (PostgreSQL `bytea`):** Rejected due to the catastrophic I/O thrashing and memory eviction issues highlighted in the context.

## Consequences

### Positive
* Protects PostgreSQL performance, guaranteeing fast standard queries.
* Offloads binary ingress bandwidth entirely from the .NET backend API servers.
* Enhances security by eliminating hardcoded connection strings via Managed Identities.

### Negative
* Hard vendor lock-in to the Microsoft Azure ecosystem for multimedia handling.
* Introduces asynchronous UI complexity (the client must handle the URL request and the subsequent direct upload).

### Risks and Technical Debt
* If a technician uploads a file directly to Azure but loses internet connection before confirming the transaction to the backend API, an "orphan blob" is created. A background scavenger script/lifecycle policy must be implemented to prune orphaned blobs.
