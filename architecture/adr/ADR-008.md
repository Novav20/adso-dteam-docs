# ADR-008: Selection of Object Storage Provider for ISO 14224 Multimedia Evidence

## 1. Status
**Approved**

## 2. Context
The CMMS Digital Twin requires field technicians to capture and upload high-resolution photographic and video evidence linked to specific `FailureRecords` (ISO 14224 compliance). Storing these binary payloads natively inside the PostgreSQL database using `bytea` (Relational BLOB storage) introduces severe operational bottlenecks:
* Rapidly saturates PostgreSQL `shared_buffers` causing cache eviction of hot index pages.
* Explodes Write-Ahead Log (WAL) generation, causing I/O thrashing.
* Exponentially inflates database backup and restore times (violating RTO/RPO objectives).

To protect relational database performance, the architecture must adopt the **Valet Key Pattern**, where the .NET 10 API acts as an authorization broker, providing the client with a Time-Limited Signed URL to upload the payload directly to a specialized cloud Object Store. The database will only store the resulting file URI.

## 3. Options Evaluated

### Option A: AWS S3
Amazon S3 is the industry standard for object storage. It offers Presigned URLs for direct client uploads and provides an official .NET SDK (`AWSSDK.S3`).
* **Pros:** Highly resilient, ubiquitous, standard S3 API used by many open-source clients.
* **Cons:** Security context management (IAM) requires mapping AWS credentials into the .NET host environment, adding slight friction compared to native Microsoft identity solutions.

### Option B: Azure Blob Storage
Microsoft Azure's native object storage service. It utilizes Shared Access Signatures (SAS) to grant time-limited upload permissions.
* **Pros:** Perfect synergy with the .NET 10 ecosystem. The `Azure.Storage.Blobs` SDK is optimized for modern C# asynchronous streams. It integrates seamlessly with **Microsoft Entra ID (Managed Identities)**, allowing the ASP.NET Core API to authenticate to the storage account without ever storing connection strings or secret keys.
* **Cons:** Vendor lock-in to the Microsoft cloud ecosystem.

## 4. Decision
We have selected **Option B: Azure Blob Storage**.

Given that the core backend technology stack is built on **.NET 10 and C#**, staying within the Microsoft Azure ecosystem offers the most frictionless integration path. The ability to use Managed Identities via `DefaultAzureCredential` in ASP.NET Core eliminates the security risks of hardcoded access keys. Azure Blob Storage perfectly satisfies the Valet Key pattern requirements by generating user-delegated SAS tokens, keeping binary traffic completely off the .NET 10 API servers.

## 5. Consequences
* The `media_attachments` table in PostgreSQL will only store the generated Azure Blob URI (`file_url`).
* The UI/Mobile client must be capable of executing HTTP PUT requests directly to Azure Blob Storage using the provided SAS token.
* A new functional port (`media_repo`) must be added to the Component Architecture to represent the Azure Blob Storage dependency.
