# UC-INV-007: Validate and Activate Master Asset (Commissioning)

## Use Case Template

| **Element** | **Detail** |
| :--- | :--- |
| **ID** | UC-INV-007 |
| **Name** | Validate and Activate Master Asset (Commissioning) |
| **Primary Actor** | Reliability Engineer |
| **Secondary Actors** | N/A |
| **Description** | Validates and formally approves the technical inclusion of a physical asset (Equipment Unit, Level 6) into the operational ecosystem. It enforces strict completeness checks (Commissioning Gate), ensuring that critical parameters such as LOTO procedures, physical boundaries, and design attributes are fully documented before the asset is exposed to the Maintenance (MTTO) and Digital Twin (VIS) modules. |
| **Preconditions** | <ul><li>The Engineer is authenticated in the system with the "Reliability Engineer" role [[TR-006]].</li><li>The asset is registered in the catalog in a preliminary/draft status.</li><li>The asset has a Functional Location defined in the system.</li></ul> |
| **Main Flow** | 1. The Engineer accesses the inventory control panel and selects the "Assets Pending Validation" view.<br>2. The System displays a list of equipment in preliminary status, ordered by waiting time.<br>3. The Engineer selects a specific asset for review.<br>4. The System presents the complete technical data sheet, applying redundant coding (Shape + Color) to highlight the missing mandatory attributes according to the asset class.<br>5. The Engineer enters or edits the required technical parameters (e.g., class design attributes, technical manuals association).<br>6. The Engineer selects the "Authorize Activation" action.<br>7. The System executes a strict gate validation (Commissioning Gate), verifying that the asset complies with:<br>   - Valid link to a Functional Location.<br>   - Criticality and Safety Critical Equipment (SCE) flag defined.<br>   - Physical boundaries and logical components (Level 8) structured.<br>   - Isolation points (LOTO) mapped to guarantee safe operations.<br>8. Upon passing validation, the System:<br>   - Invokes domain logic to transition the asset status to operational and automatically stamps the current "Start of operation date" for MTBF calculations.<br>   - Atomically persists the change in the database, enabling the asset for maintenance planning and visualization in the Digital Twin.<br>   - Records the transaction in the immutable audit trail [[TR-001]] via an append-only log with its chained cryptographic integrity hash.<br>9. The System displays a success confirmation and removes the asset from the review queue. |
| **Alternate Flows** | **AF-001: Technical Rejection due to Inconsistencies**<br>In step 6, if the Engineer determines that the engineering data is incorrect or the physical installation presents unrecoverable deviations:<br>   1. The Engineer selects the "Reject Asset" action.<br>   2. The System requires the mandatory input of a technical reason justifying the return.<br>   3. The Engineer enters the reason and confirms the rejection.<br>   4. The System invokes domain logic to transition the asset to rejected status, permanently blocking its exposure in the Digital Twin views and persisting the entered reason.<br>   5. The System generates the entry in the immutable audit [[TR-001]] and dispatches an asynchronous notification to the user responsible for the initial entry for correction.<br>   6. The flow ends and the System returns to the pending list.<br><br>**AF-002: Activation Block due to Incomplete Data (Gate Failure)**<br>In step 7, if the System detects that mandatory fields or security configurations are still missing (e.g., LOTO not defined):<br>   1. The System blocks the transition to operational status applying the completeness regulatory restriction of ISO 14224 / ISO 45001.<br>   2. The System alerts the user detailing exactly which engineering or security parameters are missing, using warning iconography and high contrast colors (WCAG 2.1 AA).<br>   3. The flow returns to step 5 so the Engineer can complete the required technical information. |
| **Postconditions** | <ul><li>The asset is formally activated, with its service date stamped, and exposed to the platform's functional modules (MTTO, VIS).</li><li>It is guaranteed that no asset operates without LOTO configuration and defined physical boundaries.</li><li>The immutability of the decision (approval or rejection) is preserved through the cryptographic log.</li></ul> |
| **Associated Requirements** | FR-137, FR-138, FR-139, FR-140, FR-141, NFR-144, NFR-145, [[TR-001]], [[TR-008]], [[TR-011]] |
