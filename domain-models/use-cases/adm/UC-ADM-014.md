# UC-ADM-014: Manage User Lifecycle and Authentication Identity

## Use Case Template

| **Element** | **Detail** |
| :--- | :--- |
| **ID** | UC-ADM-014 |
| **Name** | Manage User Lifecycle and Authentication Identity |
| **Primary Actor** | System Administrator |
| **Secondary Actors** | End User (in recovery flows) |
| **Description** | Manages the complete lifecycle of corporate user accounts (provisioning, updates, logical deletion) and enforces the technical configuration of secure identity policies (password complexity algorithms, expiration, session limits, and anti-brute force mechanisms). It guarantees the referential integrity of transactional records by prioritizing logical deactivation over physical deletion. |
| **Preconditions** | <ul><li>The Administrator is authenticated in the web console with an authorized identity management role [[TR-006]].</li><li>The role matrix is fully configured and available for assignment.</li></ul> |
| **Main Flow** | 1. The Administrator accesses the User Management directory and selects "Create New Account".<br>2. The System presents the identity form requiring basic corporate data (Name, Surname, Corporate Email, Technical ID/Employee Code).<br>3. The Administrator completes the data and assigns one or more configured Roles to the user.<br>4. The Administrator selects the account provisioning mode (e.g., sending an activation link to the user's email).<br>5. The Administrator confirms the registration.<br>6. The System executes uniqueness validations, ensuring that the corporate email and Technical ID do not exist in the database.<br>7. The System invokes the persistence service:<br>&nbsp;&nbsp;&nbsp;- Registers the user securely, initializing their status as "Pending Activation".<br>&nbsp;&nbsp;&nbsp;- Links the assigned roles via an associative data structure.<br>&nbsp;&nbsp;&nbsp;- Generates the immutable audit record [[TR-001]] detailing the provisioning action and the assigning Administrator.<br>8. The System generates a single-use cryptographic token, embeds it in an activation email, and dispatches it to the new user.<br>9. The user receives the email, accesses the secure link, and establishes their initial password, which is evaluated against strict length and complexity policies.<br>10. The System completes the activation and updates the user's status to "Active". |
| **Alternate Flows** | **AF-001: Secure Deactivation (Logical Deletion)**<br>If the Administrator needs to remove a user (e.g., contract termination):<br> 1. The Administrator selects the active account and executes the "Deactivate User" action.<br> 2. The System requires an administrative justification.<br> 3. The Administrator confirms the action.<br> 4. The System applies a logical deletion (changes status to INACTIVE) keeping the user's historical relations intact in work orders and audit logs.<br> 5. The System immediately revokes and invalidates all active sessions and access tokens for that user.<br> 6. The System records the deactivation in the immutable audit [[TR-001]].<br><br>**AF-002: Brute Force Mitigation (Automatic Intervention)**<br>During any user's authentication process:<br> 1. The System detects multiple consecutive login attempts with invalid credentials.<br> 2. Upon exceeding the configured maximum failure threshold, the System automatically blocks the account for a specific period of time (e.g., 15 minutes).<br> 3. The System dispatches a security alert to the user's email notifying them of the preventive block.<br> 4. The System isolates the event by recording it as a security anomaly in the immutable log.<br><br>**AF-003: Password Recovery and Complexity Validation**<br>If an unauthenticated user requests to restore their access:<br> 1. The User enters their email in the portal and requests recovery.<br> 2. The System validates that the account exists and is not logically deactivated.<br> 3. The System generates a single-use token with temporal validity and sends it via email.<br> 4. The User accesses the link and enters their new password.<br> 5. The System evaluates the credential. If it does not meet the minimum length (12 characters) or violates the non-reuse policy, the System stops the process and indicates the specific reasons for rejection.<br> 6. After a successful validation, the System securely updates the credential, invalidates the recovery token, and notifies the user of the update. |
| **Postconditions** | <ul><li>The user's lifecycle (creation, block, or deactivation) is updated, guaranteeing the protection of system resources.</li><li>Access revocation takes immediate effect on any active session.</li><li>All identity mutations, breach attempts, and blocks are cryptographically traced for forensic audits.</li></ul> |
