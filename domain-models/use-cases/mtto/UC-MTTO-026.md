# UC-MTTO-026: Calculate RIME Priority of Work Requests (Backlog)

## Use Case Template

| **Element** | **Detail** |
| :--- | :--- |
| **ID** | UC-MTTO-026 |
| **Name** | Calculate RIME Priority of Work Requests (Backlog) |
| **Primary Actor** | Maintenance Planner |
| **Secondary Actors** | Reliability Engineer (notified) |
| **Description** | Automatically calculates and assigns an objective priority score to each work request in the backlog, delegating the calculation to the RIME (Ranking Index for Maintenance Expenditure) prioritization engine implemented under the *Strategy* pattern (`IRimeCalculator`, [[ADR-002-RIME-MVP-Static-Factors|ADR-002]]). In the MVP strategy, the score is calculated deterministically from Asset Criticality (1-10) and Work Class weight (1-10). The system consolidates resource availability (materials and time) to facilitate decision-making. |
| **Preconditions** | <ul><li>The Planner is authenticated in the web system with the "Maintenance Planner" role [[TR-006]].</li><li>There are pending work requests in `NEW` status to be planned.</li><li>The affected assets have a numerical Criticality value (1 to 10) configured in their technical data sheets.</li></ul> |
| **Main Flow** | 1. The Planner accesses the "Backlog Management" module in the web portal and selects "View Pending Requests".<br>2. The System retrieves all pending work requests.<br>3. The System automatically calculates the priority index for each request by invoking the active strategy of the `IRimeCalculator` service ([[ADR-002-RIME-MVP-Static-Factors|ADR-002]]):<br>   - In the standard MVP strategy, it obtains the asset criticality from the master catalog and the weight of the selected Work Class, multiplying both factors to generate the resulting score (Range: 1 to 100).<br>4. The System classifies and groups the request into a high-contrast visual category based on the obtained score:<br>   - **Do First** (80-100): Emergency Category.<br>   - **Schedule** (50-79): High Category.<br>   - **Plan** (20-49): Normal Category.<br>   - **Wish** (1-19): Low Category.<br>5. The System sorts the backlog descendingly by RIME score, enriching each row with key operational metadata: Equipment Serial Number, Maintainable Item (Level 8), Estimated Man-Hours (Wrench Time) and Material Availability Status.<br>6. The Planner visualizes the prioritized list and confirms the distribution of the weekly workload. |
| **Alternate Flows** | **AF-001: Work Class Modification (Priority Adjustment)**<br>If the Planner detects that a request requires greater or lesser urgency due to operational conditions:<br>   1. The Planner edits the "Work Class" field, changing (for example) from "Preventive Maintenance" to "High Process Priority".<br>   2. The System immediately recalculates the RIME score and automatically reorders the backlog list.<br>   3. The System records the transaction in the immutable audit trail [[TR-001]] generating an append-only record with its corresponding chained cryptographic integrity hash, capturing: user, request identifier, old value, new value, new calculated score and technical justification.<br><br>**AF-002: Asset without Defined Criticality (Fail-Safe)**<br>If the work request is associated with an asset that lacks criticality classification in its technical data sheet:<br>   1. The System applies the fail-safe principle. To prevent the purely multiplicative calculation from burying the request, the final RIME score is forced to a minimum floor of 75 (High Category), regardless of a low Work Class weight.<br>   2. The System highlights the request with a prominent visual warning: "Criticality not configured on the asset. Maximum temporary priority assigned preventively."<br>   3. The flow continues to step 4, sending a notification to the Reliability Engineer to configure the actual criticality in the catalog. |
| **Postconditions** | <ul><li>All pending work requests have a RIME score calculated and audited at runtime.</li><li>The backlog is objectively sorted with estimated resources (labor and materials) visible for scheduling.</li><li>Any alteration of priority parameters is cryptographically recorded.</li></ul> |
